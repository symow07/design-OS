### A71. Answer to your question: A. But the column records instrument competence, never route.

Your instinct in B is the right instinct and it is guarding against the right thing. Pre-sorting 92
sites by *how you expect them to come out* would be reading-ahead, and it would be the worst kind —
a disposition smuggled in as a schema.

But that is not what the split is. Look at what the two families actually name:

- **Firing-auditable** — the site is a runtime expression that can fire, so the competent
  instrument is an execution-behaviour audit over retained records or a trace.
- **Declaration-checkable** — the site is a value stated once, so the competent instrument is a
  record comparison against a contract.

That is a claim about **which instrument is competent for the claim type**, which is 1s, decided by
the shape. It is not a claim about what the instrument will find. 1s already requires this
determination before any disposition is attempted; putting it in a column makes it explicit and
checkable rather than re-derived by whoever picks the site up.

Three conditions, and they are what keep A from becoming B's fear:

1. **Derived, not assigned.** The union gate's baseline already keys on file, symbol **and shape**.
   The family is a projection of the shape field through a declared shape → family table. Nobody
   looks at a site and judges its family. If the mapping is ever applied by hand to a site, that is
   A66 at third order and it is a defect.
2. **The table is declared before it is applied**, and any shape that maps to neither family is a
   **finding**, not a default — it means the gate enumerates a shape no instrument is competent for,
   and that is reported at the boundary.
3. **The column carries no dispositional weight.** A site is not discharged, deferred or narrowed by
   which column it sits in. Either consumer may find a site in the other column and must take it.
   The column routes work; it never closes it.

Under those conditions the split is bookkeeping over data already computed, and the manifest gate
and the layout node each pull their kind without either of them inheriting a judgment.

The conclusion may well be right. The number is not established, and the reason is the programme's

of that class.** Say so in the record.

### A74. The repair removes the default. It does not align it.

`lid_roof_mm` declares 1.5 in the case contract and defaults to 1.6 in code. The obvious repair is
to change 1.6 to 1.5. **Do not do that.**

Under 1y a default is a statement of the value regardless of syntax. Changing 1.6 to 1.5 converts a
`DECLARED_CONFLICTING` site into a `DECLARED_AGREEING` one — and `DECLARED_AGREEING` is not a
repaired state, it is the state this defect was in before someone moved the contract. Two statements
of one value that agree today are two statements that can disagree tomorrow, silently, with no
instrument watching the gap. The whole defect was the gap, not the 0.1.

So the repair is: **the in-code default is removed, and the consumer reads the contract or raises.**
A missing key becomes a loud failure rather than a quiet 1.6. That converts the class from
"detectable by census" to "impossible by construction," which is the disposition A23 gave the
identity-zero constant and the disposition this programme gives every class that has cost it a
number.

If any call site genuinely cannot reach the contract, that is a finding about the plumbing and it is
reported — it is not a licence to leave the default in.

### A75. The void list depends on A72, so the containment check runs first, inside this node.

You asked whether the ledger bookkeeping delays the repair. It does not, and it also is not
optional, because of what VALUE_MOVING requires.

A VALUE_MOVING node carries an **explicit void list of the committed numbers it moves**. The void
list is drawn from the ledgers. If the ledgers' containment relation is unknown, the void list
cannot be shown complete — you would be voiding numbers enumerated against a population that may
have a third part. So the containment check is not a competitor to the repair; it is a
**precondition of the repair's own deliverable**, and it costs nothing but a set operation on two
files already committed.

Ordering follows: containment, then the repair, in separate commits, with the void list computed
after containment closes.

go with the layout audit into the slot alongside the render queue, on the same reasoning A68 gave:
